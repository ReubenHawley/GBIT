Executive overview

GBIT is a verification orchestration engine—not a replacement for existing test frameworks. It determines the impacted test set after a change using typed, versioned dependency relationships, then delegates execution to existing runners such as xUnit, pytest, Jest, and JUnit.

Design principle: Every change has an impact surface. Every test provides evidence about some portion of that surface. GBIT links the two, selects relevant tests, and explains why the selection is appropriate.
High confidenceFeasibilityLanguage-neutral graph kernel and pluggable analyzers/runners are achievable.
Medium confidenceEfficiencyLarge CI savings are plausible, but vary with graph density and test-suite structure.
Major uncertaintyCompletenessDynamic calls, generated code, distributed state, and unknown dependencies require safe fallback.

The architecture prioritizes correctness over optimization. An unknown dependency expands the selected set; it does not justify excluding tests. Continuous shadow-mode validation is used to discover missed relationships.

01

Acceptance criteria

Success must be defined before implementation. The fundamental quality target is regression detection equivalence—a selected test set should detect the failures the full suite would have detected, within the stated evidence and safety policy.

02

System architecture

Implement the core as a modular monolith with out-of-process plugins. The executable works locally or in CI, while plugins can be written in any language that implements the protocol.

ComponentResponsibilityLanguage-specific?
Change detectorCompare two repository revisions and identify changed artifactsNo
Analyzer pluginsDiscover symbols, static dependencies, contracts, and observed relationshipsYes
Graph engineNormalize, version, index, and traverse evidence-backed relationshipsNo
Selection engineCompute affected tests, widen for uncertainty, produce explanationsNo
Runner pluginsDiscover tests and execute runnable subsets using native frameworksYes

The core never needs to understand C# methods, Python decorators, JavaScript imports, or JUnit selectors. It understands artifact identities, changes, directed dependencies, test identities, and evidence validity.

03

Graph model

Use a typed property graph built from versioned evidence. A file-only dependency graph is too coarse for precise, high-confidence selection.

Source entities

Repositories, projects, source files, functions, types, methods, modules.

Verification entities

Tests, parameterized test cases, fixtures, suites, evaluation scenarios.

Contract entities

APIs, schemas, database tables, events, messages, interfaces.

Environment entities

Build targets, package versions, configuration, feature flags, toolchains.

3.1 Relationship types

Use consistent direction for a dependency relationship: Consumer → Dependency. Thus CheckoutService → PricingService represents CheckoutService depending on PricingService. Additional typed relationships can describe verification and execution observations, with their semantics explicit.

3.2 Cross-language propagation

A versioned baseline graph is essential. When an entity is removed, its former consumers may only appear in the parent revision; analyzing the new tree alone would miss them.

04

Plugin architecture

Define a versioned contract that allows plugins written in any language to communicate with the core. Begin with JSON-RPC over stdio for simple out-of-process execution; add a gRPC transport only when performance or remote execution demands it.

Plugin capabilityInputOutput
Language analyzerSource tree / changed filesSymbols, definitions, references, possible call edges
Build analyzerBuild manifests and dependency metadataProject graph, build targets, package dependencies
Contract analyzerOpenAPI, JSON Schema, migrations, event schemasCross-module relationships
Test discovererTest workspaceStable test IDs, metadata, runner capabilities
Evidence collectorInstrumented test executionPer-test code observations and runtime edges
Test runnerExecution planTest outcomes, timing, artifacts, execution identifiers

4.1 Illustrative plugin manifest

{
  "apiVersion": "gbit.plugin/v1",
  "id": "gbit.analyzer.dotnet",
  "version": "0.1.0",
  "capabilities": [
    "symbols",
    "references",
    "incremental-analysis"
  ],
  "languages": ["csharp"],
  "methods": [
    "initialize",
    "analyze",
    "getCapabilities"
  ]
}

Plugin processes report capabilities, receive repository revision and workspace context, and return normalized graph entities and evidence. Plugins that support several capabilities can implement them together.

4.2 Existing infrastructure to reuse

  • SCIP: a language-independent Protobuf code-intelligence format that already represents definitions and references, reducing bespoke symbol indexing.
  • Tree-sitter: practical cross-language incremental parsing fallback when precise semantic indexers are not available.
  • Native compiler/build APIs: richer source and project relationships for languages that expose them.
  • Native runner adapters: test discovery/filter syntax remains owned by pytest, xUnit, JUnit, Jest, and similar systems.
Boundary: SCIP and Tree-sitter do not, by themselves, provide a complete behavioral dependency graph. Missing runtime, configuration, and dynamic relationships must remain visible as uncertainty.

4.3 Plugin isolation and security

Plugins should run with pinned versions, restricted filesystem and network access, bounded CPU/memory, explicit timeouts, and no CI secrets unless strictly required. Treat repository-defined plugin executables on untrusted pull requests as untrusted code. A required plugin failure must fail or safely widen verification, never silently return an empty dependency set.

05

Test selection engine

The planner consumes a change set, base/head graph snapshots, discovered test inventory, and a safety policy. Its output is a deterministic, explainable execution plan.

5.1 Formal selection model

Let C be changed entities; Gb and Gh be baseline and proposed-revision graphs; R(C) be reverse-reachable entities using relevant edges from both snapshots; and T be all discovered tests.

Selection: Trun = Tchanged ∪ Trelated ∪ Tfallback.

Trelated comprises tests associated with the affected surface through dependency or verification evidence. Tfallback contains tests required because analysis cannot confidently bound impact. Edge traversal rules must be type-aware: consumer dependencies and verification observations are not automatically interchangeable.

5.2 Selection versus execution granularity

A graph may identify one affected parameterized test, but the native runner may only offer a stable selector for its class or file. GBIT must distinguish requested test cases from actual runnable units and record both in the plan.

5.3 Minimum execution-plan schema

  • Input base/head revisions and graph snapshot IDs.
  • Policy, analyzer versions, and completeness status.
  • Selected test identities and translated runner selectors.
  • Coverage gaps, fallback boundaries, and excluded tests.
  • Per-test causal paths and provenance references.
  • Predicted versus actual execution counts and durations.
06

Correctness, evidence and safety

Code change impact is not fully captured by static references. The engine should combine several evidence classes while retaining their separate limitations.

EvidenceUseful forLimitation
Semantic/static analysisPotential dependencies before code executesReflection, dynamic dispatch, runtime configuration
Per-test runtime coverageObserved test-to-code execution linksHistorical observations cannot prove new paths are impossible
Contract/build relationshipsCross-module and cross-language impactOften coarse and can miss behavioral coupling
Per-test coverage requirement: Aggregate coverage is insufficient for exact Test → Code mapping. GBIT requires per-test execution contexts, trace correlation, or equivalent instrumentation; otherwise it must plan at a coarser granularity.

6.1 Operating policies

ModeBehaviorBest use
ShadowCompute selected tests; execute all tests; compare resultsInitial rollout and validation
ConservativeExecute impacted tests plus widened uncertain scopesProtected branches and mainline
OptimizedUse precise, validated relationships under explicit policyEstablished codebases with sound evidence

6.2 Self-validation

Continuously compare selection predictions with full-suite executions on designated builds. Measure:

  • Regression miss rate: fraction of failure-detecting tests that GBIT omitted, evaluated against known faulty changes.
  • Selection efficiency: wall-clock time saved after indexing, planning and CI orchestration overhead.
  • Fallback rate: proportion of changes requiring conservative widening.
  • Explanation completeness: proportion of decisions with reproducible causal paths and evidence metadata.

Replay historical regressions and use controlled mutation testing to enrich the dataset. Include interface changes, configuration shifts, schema changes, reflection, generated code and package upgrades. A test that has never observed a new branch cannot establish that the branch is safe to skip.

Core safety invariant: When dependency analysis is incomplete, GBIT must widen the selected test boundary or refuse optimized execution. An empty test selection is not automatically a valid passing result.
07

Persistence and scalability

Use SQLite with adjacency indexes for an initial embedded engine. A specialized graph database is not necessary until workloads demonstrate that graph traversal or multi-user concurrency requires one.

Logical table/storeContents
EntitiesCanonical IDs, entity types, locations, versions
RelationshipsDirected edges with types, validity, provenance
GraphSnapshotsCommit/revision mapping, indexing metadata
TestInventoryDiscovered tests and executable identities
CoverageEvidencePer-test observations by revision and environment
ExecutionHistoryOutcomes, durations, flakiness, regression signals
SelectionPlansSelected and deferred tests, explanation paths and policies

Incremental indexing should use content hashes and invalidate affected relationships based on compiler settings, plugin versions, repository revisions, and configuration. Runtime evidence must be scoped to the build and instrumentation environment that produced it.

For an optional centralized deployment, PostgreSQL is a reasonable scaling step before introducing another storage engine.

08

Developer experience

GBIT should require minimal configuration for a conventional repository. The CLI discovers installed capabilities, creates an index, plans a test run, executes through native adapters, and explains decisions.

# Discover projects, analyzers and available test runners
gbit init

# Build the initial graph and collect baseline evidence
gbit index --full

# Show impacted tests for the current branch
gbit plan --base origin/main --head HEAD

# Execute the selected tests
gbit test --base origin/main --head HEAD

# Explain why a test was selected
gbit explain test:checkout-discount

# Visualize the affected graph
gbit graph --affected

# Verify the planner against the full test suite
gbit verify --full

The explain command should support both “Why was this test included?” and “Why was this test excluded?” The latter must state the bounds of analysis rather than presenting absence of a discovered edge as absolute proof of independence.

09

Test-first implementation roadmap

01

Graph kernel and conformance suite

Implement change modeling, typed graph, snapshots, dependency traversal, safety policies and explanation paths. Write synthetic graph acceptance tests first.

Exit: All language-neutral selection, versioning, deletion, uncertainty and determinism scenarios pass.
02

Two independent language ecosystems

Implement C#/.NET and Python/pytest analyzers and runner plugins. Integrate SCIP where supported. Enforce protocol conformance and independent plugin deployment.

Exit: Both ecosystems use the exact same core planning engine on real repositories, with reproducible selected test execution.
03

CI shadow-mode validation

Integrate GitHub Actions and Azure DevOps. Record full-suite execution, compare planned subsets, replay historical changes and inject mutations.

Exit: Empirical missed-regression and wall-clock metrics meet an explicit rollout threshold across representative projects.
04

Cross-language impact and optimized CI

Add TypeScript analysis, OpenAPI/JSON Schema propagation, per-test runtime instrumentation and conservative selective execution.

Exit: Contract changes select appropriate tests in other languages and CI safely enforces the computed plan.

11

Differentiation and positioning

Regression test selection is an established field. Existing tools such as Nx and pytest-testmon already provide forms of change-aware execution. A generic “run fewer tests” claim would not be defensible differentiation.

GBIT's stronger proposition is combining fine-grained cross-language dependencies, externally pluggable analyzers and runners, first-class contracts, explicit evidence provenance, conservative uncertainty handling, and ongoing verification of its own selection decisions.

Product direction: evolve GBIT into a change-impact verification platform capable of selecting conventional tests, integration validations and eventually agent evaluations affected by code, tools, prompts, schemas and workflow changes.

For agent-native systems, extending the graph with prompts, model configurations, MCP tools, workflow transitions and evaluation datasets provides a direct path beyond source-code-only test selection. That extension should follow—not precede—validation of the core graph kernel.

12

Architectural decisions to lock in

  1. Language-neutral kernel: the planner has no language or test-framework specific implementation logic.
  2. Versioned graph and provenance: evidence belongs to explicit revisions and analyzer versions.
  3. Independent plugins: analyzers and runners can be installed and upgraded separately from the core.
  4. Correctness before optimization: uncertain relationships expand execution, never silently justify exclusions.
  5. No mandatory cloud dependency: indexing, planning and execution work offline or inside existing CI.
  6. Baseline/head-aware impact: deleted and changed relationships are traversed using both revisions.
  7. Selection separated from execution: native runner capability determines the final runnable granularity.

Immediate next deliverable

Build the GBIT conformance repository: language-neutral graph fixtures, expected impact sets, safety and deletion scenarios, plugin protocol tests, and a deterministic planner baseline. Treat these acceptance tests as the executable architecture specification, then implement the kernel and plugins until all tests pass.
